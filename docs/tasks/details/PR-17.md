# PR-17: Financial ledger reconciliation and durable mutation idempotency

- Phase: production_hardening
- Owner role: coordinator
- Dependencies: CORE-22, CORE-25, OPS-09
- Owned paths: `app/expense-core/src/main/kotlin/com/subhrodip/squarewise/expensecore/expenses/`, `app/expense-core/src/main/kotlin/com/subhrodip/squarewise/expensecore/settlements/`, `app/expense-core/src/main/resources/db/migration/`, focused Expense Core tests, and this task detail

## Objective

Close CRIT-01 and CRIT-02 from the production-readiness audit by making
settlements first-class ledger effects and persisting mutation idempotency
atomically with financial side effects.

## Requirements

- Recording a settlement writes balanced participant postings in the same
  transaction as the settlement record.
- Reversing a settlement writes exactly one compensating posting set and is
  idempotent under retries.
- Balance aggregation includes active expense and settlement postings using one
  authoritative posting stream.
- Expense creation persists an idempotency key scoped to group, actor, and
  operation; same-key same-payload requests replay the original response and
  altered payloads fail with a conflict.
- Database uniqueness and transactional tests cover concurrent duplicate
  requests and unknown-outcome replay.
- A reconciliation test/procedure proves zero-sum postings and settlement/
  expense coverage without relying on in-memory stores.

## Current increment

Registered after confirming that `JpaSettlementStore` did not create ledger
postings and `JpaExpenseStore.create` discarded its idempotency key. No
implementation claim is made until the focused tests and PostgreSQL evidence
pass.

The settlement path now writes two participant postings for each recorded
settlement and compensating postings exactly once on reversal. Expense creation
now stores a scoped SHA-256 payload fingerprint and replays the original
expense for an identical key while rejecting altered payloads. `V10` adds the
settlement posting reference and `V11` adds the durable idempotency table.
`JpaSettlementStoreTest` proves the recorded and reversal posting sets are
balanced, contain the expected participant signs, and are unchanged by a
repeated reversal. Focused settlement and expense JPA suites pass; concurrent
PostgreSQL idempotency evidence and a dedicated reconciliation report remain
open. The operator procedure is documented in
`docs/operations/ledger-reconciliation.md`; execution evidence against the
local Compose `squarewise_expense_core` database returned zero non-zero group
ledgers, zero uncovered active expenses, and zero invalid settlements. The
database contained zero settlements at execution time, so populated-settlement
evidence remains required against a representative release dataset.

The expense-create path now acquires the pessimistic group lock before reading
or creating the scoped idempotency claim. Same-group same-key requests
therefore serialize before the unique claim is persisted, closing the local
check-then-insert race. An opt-in `PostgresExpenseIdempotencyConcurrencyTest`
now exercises the lock, durable claim count, and single posting set against the
Compose PostgreSQL datasource. With `SQUAREWISE_POSTGRES_TESTS=true` and the
local `squarewise_expense_core` database, the test passed. The focused
`JpaExpenseStoreTest` suite also passes.

The concurrency test was re-run against the local Compose PostgreSQL database
with the documented datasource settings and passed again. The read-only ledger
reconciliation queries returned zero non-zero group ledgers, zero uncovered
active expenses, and zero invalid settlements; the database contained zero
settlements at execution time, so populated-settlement evidence remains open.
