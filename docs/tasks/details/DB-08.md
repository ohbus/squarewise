## Current implementation increment

`ProfileController` scopes `/me`, public profile-by-ID, and bounded batch lookup
as explicitly reader-eligible operations. `/me` reads an existing profile and
does not provision one; if the selected reader is unavailable or behind a
causal watermark, the bounded writer fallback preserves the requested
consistency. Accounts has named writer/profile reader configuration, while
authentication, sessions, rate limits, and profile mutation remain unchanged on
the writer.

## Route evidence (2026-09-22)

`ProfileControllerTest` records the profile adapter context and asserts
`profile.lookup` is a `QUERY` with `EVENTUAL` consistency and explicit reader
eligibility. The `/me` path is reader-bound through `profile.me`; causal
watermarks and replica health can still select the writer fallback. Replica
outage and read-after-write integration evidence remain open.

`ProfileQueryStore` and `ProfileCommandStore` now separate bounded profile
reads from writer-side update/deletion transitions; `ProfileStore` remains a
compatibility facade for existing adapters.
