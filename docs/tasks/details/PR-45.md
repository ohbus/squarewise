# PR-45: Lock recurring schedules during worker claims

- Phase: production_hardening
- Owner role: coordinator
- Dependencies: PR-17, PR-18
- Owned paths: Expense Core recurring repository/service/tests, migration-independent task detail, and progress evidence

## Objective

Prevent multiple Expense Core replicas from processing the same due recurring
schedule concurrently.

## Acceptance criteria

- Due schedules are selected with a database pessimistic write lock.
- The lock is held by the existing transactional worker batch through occurrence
  generation and schedule advancement.
- Existing recurring schedule behavior and tests remain passing.

## Validation

- `./gradlew.bat :app:expense-core:test --rerun-tasks --no-daemon`
- `git diff --check`

## Current increment

The due-schedule query now uses a database `PESSIMISTIC_WRITE` lock. The
existing transactional worker holds that lock through occurrence generation
and next-date advancement, preventing another replica from processing the same
due schedule concurrently. The full Expense Core test suite passed.
