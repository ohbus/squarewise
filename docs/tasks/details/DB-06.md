# DB-06: Split Expense Core command and query ports

Separate application command/query ports and handlers for groups, membership,
expenses, settlements, search, recurring work, synchronization, audit, and
outbox. Preserve aggregate transaction boundaries and writer-only financial,
authorization, lock, claim, idempotency, and revision operations.

Acceptance proves no controller/service selects a datasource, commands cannot
use readers, DTOs replace entity leakage, all result sets are bounded, and
existing Expense Core tests plus PostgreSQL concurrency tests pass.

## Concrete code targets

- Split `expenses/ExpenseStore.kt` into command/query-facing ports while preserving compatibility adapters during migration.
- Refactor `JpaExpenseStore.kt` methods into command handling versus read projection methods; inspect its create/update/delete/materialization methods and read methods near the existing read-only transactions.
- Refactor `groups/GroupStore.kt`/`JpaGroupStore.kt`, `settlements/SettlementStore.kt`/`JpaSettlementStore.kt`, `sync/JpaSynchronizationStore.kt`, `search/SearchStore.kt`/`JpaSearchStore.kt`, and recurring service/repositories.
- Mark `GroupRepository.findLockedByGroupId`, `OutboxRepository` locks, `RecurringExpenseScheduleRepository` due claims, idempotency lookup/claim, and settlement recording as writer-only operation metadata.
- Update `ExpenseController`, `GroupController`, `SearchController`, `SettlementController`, `SyncController`, and recurring controllers only to call handlers, never route databases.
- Extend `JpaExpenseStoreTest`, `JpaGroupStoreTest`, `JpaSettlementStoreTest`, `JpaSearchStoreTest`, and the existing PostgreSQL concurrency tests with route assertions.

## Implementation increment (2026-09-21)

`expenses/ExpenseStore.kt` now exposes separate `ExpenseCommandStore` and
`ExpenseQueryStore` ports, and `groups/GroupStore.kt` applies the same split
for group/membership commands and reads. The existing `ExpenseStore` and
`GroupStore` interfaces compose their ports as compatibility facades, so
current handlers and in-memory/JPA implementations continue to preserve their
transaction boundaries while new callers can depend on the narrow side they
require. No controller selects a datasource, and these increments do not move
financial or authorization reads/writes away from the writer.

Settlement persistence is explicitly writer-only through
`SettlementCommandStore`, with `SettlementStore` retained as the compatibility
facade. Synchronization now separates writer-side change append/delete commands
from bounded snapshot queries through `SynchronizationCommandStore` and
`SynchronizationQueryStore`.

The transactional outbox is similarly divided into writer-side
`OutboxCommandStore` operations (`append`, claim, acknowledge, and reject) and
the read-only `OutboxQueryStore.snapshot` operation, while `OutboxStore`
remains the compatibility facade. This keeps claiming and status transitions
writer-bound and prevents a reader from becoming a message-ownership source.

`RecurringExpenseService` now implements explicit `RecurringCommandStore` and
`RecurringQueryStore` ports. Due-schedule claiming, occurrence generation, and
schedule mutations remain command-side and writer-bound; schedule and
occurrence listing are bounded query-side operations without changing the
existing service transaction boundaries.

Validation: `./gradlew.bat :app:expense-core:test --rerun-tasks --no-daemon`
passed. Remaining DB-06 work includes audit boundaries, plus explicit
writer-only metadata and route assertions.

## Audit boundary increment (2026-09-22)

`JpaGroupStore` no longer depends directly on the repository implementation.
