# PR-18: Bounded persistence reads and mutation-time authorization

- Phase: production_hardening
- Owner role: coordinator
- Dependencies: PR-17, CORE-22, CORE-25
- Owned paths: `app/expense-core/src/main/kotlin/com/subhrodip/squarewise/expensecore/expenses/`, `app/expense-core/src/main/kotlin/com/subhrodip/squarewise/expensecore/groups/`, focused Expense Core tests, and this task detail

## Objective

Close the production-readiness findings for unbounded list reads and
authorization races by enforcing database-side limits and rechecking active
membership inside the mutation transaction after acquiring the group lock.

## Acceptance criteria

- Expense list queries apply a validated maximum page size in SQL/JPA rather
  than loading an unbounded result and truncating in memory.
- Category-filtered and unfiltered list paths share the same bound and stable
  ordering.
- Mutation authorization is evaluated inside the transaction against the locked
  group/member state; a membership removal racing a mutation cannot leave a
  financial side effect committed.
- Focused persistence and concurrent authorization tests prove the behavior.

## Current increment

Expense and search persistence reads now use Spring Data `PageRequest` with
database-side limits and stable creation-time ordering. The controller’s
validated 1..100 request bound is preserved, and the search adapter applies the
same bounded-read principle. The JPA mutation boundary now accepts the
authenticated subject, locks the membership row, and revalidates ACTIVE
membership after the group lock for create, update, and delete. Test
compilation passes; a dedicated concurrent removal-versus-mutation integration
test remains open. Expense payer and allocation collections are now `LAZY`, and
the `findById` and bounded `list` materializers run in read-only transactions;
unbounded repository methods were removed.

An opt-in `PostgresMembershipMutationRaceTest` now coordinates a committed
member removal against an expense create and asserts the waiting mutation fails
without balance postings. Execution requires the same PostgreSQL test profile
as the PR-17 concurrency test. It passed against local Compose PostgreSQL with
the removed member subject supplied through the public mutation authorization
path.
