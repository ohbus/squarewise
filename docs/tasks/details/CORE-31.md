# CORE-31: Recurring schedule participant membership identity and currency validation hardening

## Objective

Remediate recurring schedule entity identity mismatch, negative amounts, and unvalidated currency inputs (`AUD-04`, `AUD-06`, `AUD-07`) identified in the financial audit:
- In `RecurringExpenseService.getGroupMembers(groupId)`, fix the member selection query to retrieve `m.membershipId` (`UUID`) rather than parsing and hashing `m.subject` as a synthetic UUID.
- In `RecurringExpenseController.createSchedule` and `updateSchedule`, validate that every custom payer and allocation specifies the exact same currency as the schedule: `it.amount.currency == request.amount.currency`.
- In `RecurringExpenseService.validateCustomSpecifications`, enforce positivity on custom payer and allocation amounts: `it.amountMinor > 0` for all payers and allocations.
- Ensure that recurring occurrences generated by the background worker create balance postings referencing actual group `membershipId` values so that member balances update accurately.

## Design Patterns & Architectural Guidance

- **Domain Entity Identity Integrity**: Within Expense Core, the primary aggregate identifier for a participant in a group is `membershipId`. Synthetic or external auth identifiers (`subject`) must never cross into financial ledger postings.
- **Port & Adapter Boundary Validation**: In the REST adapter (`RecurringExpenseController`), enforce contract validation guards ensuring multi-currency integrity before invoking domain command stores.
- **Defensive Programming / Invariant Enforcement**: Recurring payments must represent strictly positive monetary transfers. Negative or zero values must be rejected at the boundary.
