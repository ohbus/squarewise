# QA-09: Optimized and Parallelized E2E Pipeline with Artifact Reuse

## Objective

Optimize, parallelize, and modernize the continuous integration (CI) End-to-End (E2E) testing pipeline in GitHub Actions to drastically reduce wall-clock execution time, prevent runner CPU waste, improve failure isolation, and establish a robust, unified gate for branch protection policies.

Specifically, this task achieves:
1. **Elimination of Redundant Gradle Compilation & Testing:** Reuses pre-compiled application `bootJar` artifacts (`app-jar-*`) produced by the upstream parallel `verify` matrix jobs rather than redundantly recompiling, testing, and packaging Java code inside the E2E runner.
2. **Partitioning of the Monolithic E2E Stage into Parallel Streams:** Decomposes the single, sequential ~45-minute E2E run into three isolated, concurrently executed jobs grouped by operational responsibility (Security/Edge, Product/Offline, and Concurrency/Chaos), cutting total wall-clock runtime down to ~5–7 minutes.
3. **Container Resource Efficiency & Parity:** Preserves full Docker Compose network DNS alias isolation and port topologies while leveraging pre-built bytecode with `infra/docker/Dockerfile.fast` (`eclipse-temurin:25-jre`) for sub-10-second container startup on ephemeral runners.
4. **Unified Aggregate Gate (`e2e-gate`):** Provides a single status check that waits for all parallel streams to finish (using `if: always()`), evaluates their individual success statuses, and presents a clear, deterministic check for GitHub branch protection.
5. **Standardized Token Acquisition (`tests/e2e/acquire_local_tokens.sh`):** Consolidates repetitive OIDC authentication logic (Keycloak service account tokens, negative-audience tokens, negative-issuer tokens, expired tokens) into a reusable, statically-typed test script.

## Architecture & Design Decisions

### 1. Artifact Reuse vs. Redundant Gradle Re-execution
- **Previous Bottleneck:** In the previous CI configuration, the `e2e` runner checked out the repository and immediately executed `./gradlew test --no-daemon` followed by `./gradlew bootJar --no-daemon`. This repeated the exact same compilation, unit test suites, and packaging tasks that had already passed during the matrix `verify` stage, wasting 3–5 minutes of runner CPU and delaying container initialization.
- **Optimized Flow:**
  - The matrix `verify` job uploads 4 application JAR artifacts:
    - `app-jar-accounts`: `app/accounts/build/libs/squarewise-accounts-0.1.0-SNAPSHOT.jar`
    - `app-jar-expense-core`: `app/expense-core/build/libs/squarewise-expense-core-0.1.0-SNAPSHOT.jar`
    - `app-jar-notifications`: `app/notifications/build/libs/squarewise-notifications-0.1.0-SNAPSHOT.jar`
    - `app-jar-bff`: `app/bff/build/libs/squarewise-bff-0.1.0-SNAPSHOT.jar`
  - The parallel E2E jobs declare `needs: [preflight, verify]` and download `pattern: app-jar-*` into `app/<service>/build/libs/`.
  - `docker compose -f infra/local/docker-compose.dev.yml up -d --build --wait` invokes `infra/docker/Dockerfile.fast`, which merely copies the pre-built JAR onto an `eclipse-temurin:25-jre` base image and launches within seconds.

### 2. Service Containers vs. Local Compose Topology Analysis
- **Evaluation:** Consideration was given to running PostgreSQL, RabbitMQ, Redis, and Mailpit as native GitHub Actions runner `services:` instead of inside Docker Compose.
- **Constraints Identified:**
  - **Internal Network DNS Aliases:** The Squarewise application microservices connect to each other and infrastructure using explicit Docker bridge network DNS aliases (`accounts-api`, `expense-core-api`, `notifications-api`, `postgres-db`, `message-broker`, `rate-limit-redis`, `idp-keycloak`). Native runner `services:` bind to `localhost` on the host runner, breaking internal inter-container communication unless complex networking overrides are injected.
  - **Chaos Fault Injection:** `test_chaos_recovery.py` explicitly tests transactional outbox durability by executing Docker CLI commands (`docker pause local-rabbitmq-1`, `docker exec local-postgres-1 psql ...`). Native runner `services:` are managed by the GitHub Actions runner agent and cannot be paused or manipulated with `docker pause`.
- **Decision:** Retain `docker compose -f infra/local/docker-compose.dev.yml up -d --build --wait` as the authoritative environment for all E2E runners. Because application compilation is eliminated and images are built from pre-existing JARs, container startup overhead is reduced to ~10–15 seconds, providing full fidelity without architectural compromises.

#### Stream A: `e2e-edge-and-security` (Est. ~3–4 mins)
- **Scope:** Protocol contracts, deployment smoke, token signature tampering, algorithm downgrade attacks, provider claim verification, invalid-subject handling, and boundary REST edge validations.
- **Suites Executed:**
  - `tests/e2e/contract-smoke.sh`: Validates OpenAPI, JSON schemas, and Compose configs.
  - `tests/e2e/test_oidc_negative.py`: Checks forged signatures (`tamper_signature`), unsupported algorithms (`tamper_algorithm`), wrong issuer, and expired tokens across all four services.
  - `tests/e2e/test_oidc_websocket_negative.py`: Probes GraphQL WebSocket connection rejection when presenting forged credentials.
  - `docker-compose.invalid-subject.yml`: Launches isolated mock provider emitting non-conforming subject claims; runs invalid-subject Bruno suite and negative probes.
  - `make e2e-rest-edge`: 86 comprehensive live HTTP boundary, pagination, RFC 7807 problem details, and idempotency tests against Accounts and Expense Core.

#### Stream B: `e2e-product-and-offline` (Est. ~4–5 mins)
- **Scope:** Complete end-to-end user journeys, live acceptance verification, contract collections, and mobile/offline synchronization resilience.
- **Suites Executed:**
  - `make acceptance-live`: 10/10 automated live acceptance criteria checks (`tests/acceptance/runner.py --require-services`).
  - `make bruno-run`: Complete 71-request, 78-assertion declarative API Bruno collection across Accounts, Expense Core, Notifications, and BFF.
  - `make e2e-live`: Full product lifecycle (`tests/e2e/test_product_journey.py`): registration, multi-currency group creation, invitation claiming, split calculation, netting, settlement recording, outbox relay dispatch, and notification inbox receipt.
  - `make e2e-offline`: Client offline simulation (`tests/e2e/test_offline_resilience.py`): client-generated UUIDs, queued mutation replay, retry idempotency, conflicting idempotency key rejection (HTTP 409), and sync cursor change feed gap recovery.

#### Stream C: `e2e-concurrency-and-chaos` (Est. ~3–4 mins)
- **Scope:** Real-time event streaming over WebSocket, concurrent race condition resolution, infrastructure failure injection, and transactional outbox self-healing.
- **Suites Executed:**
  - `make e2e-concurrency`: Real-time WebSocket connection to BFF via RFC 6455 and `graphql-transport-ws`, verifying `groupChanged` invalidation events and racing concurrent PUT mutations on shared expense versions (ensuring exactly one succeeds with HTTP 200/revision bump and the competitor receives HTTP 409 Conflict).
  - `make e2e-chaos`: RabbitMQ broker pause drill (`docker pause local-rabbitmq-1`), verifying local ACID transaction isolation in Expense Core, pending outbox records in PostgreSQL, broker unpause recovery, outbox drain daemon processing, and downstream delivery to Notifications.

#### Stream D: `e2e-gate` (Est. ~15 seconds)
- **Scope:** Aggregation and branch protection gate.
- **Behavior:** Runs on `ubuntu-slim` with `if: always() && inputs.run_e2e`. Inspects the outputs of all three streams:
  ```bash
  if [ "$edge_result" = "success" ] && [ "$product_result" = "success" ] && [ "$chaos_result" = "success" ]; then
    echo "All parallelized E2E test suites passed successfully."
    exit 0
  else
    echo "One or more parallelized E2E test suites failed or were cancelled."
    exit 1
  fi
  ```

## Acceptance Criteria

1. **Artifact Reuse:** E2E runner jobs depend on `verify` and consume pre-built `bootJar` artifacts, completely eliminating redundant Gradle compilation and unit testing in the E2E stages.
2. **Parallelized Execution:** Monolithic E2E suite is partitioned into focused, parallelized jobs (`e2e-edge-and-security`, `e2e-product-and-offline`, `e2e-concurrency-and-chaos`), reducing total wall-clock runtime by >60%.
3. **Aggregate Gate:** An `e2e-gate` job evaluates results across all parallel streams for unified branch protection reporting.
4. **Local Parity:** Local workflows (`make e2e-all`, `make ci-e2e`) preserve identical behavior and pass without regressions.
5. **Static Typing & Validation:** All Python scripts adhere strictly to static typing (`make python-typecheck`), and workflow syntax passes `make workflow-validate`.
