# DB-10: Add causal read-after-write propagation

Define and propagate a writer commit watermark through service responses and
BFF REST/GraphQL requests. A replica may serve a follow-up query only after it
has replayed the watermark; otherwise route to the writer until the deadline.

Acceptance covers command response, HTTP propagation, BFF fanout, WebSocket
hint recovery, lagging readers, timeout, and no-watermark behavior without
using wall-clock time as the causal mechanism.

## Concrete code targets

- Add watermark/value types and propagation support in `libs/db`.
- Add response/request metadata handling in Accounts, Expense Core, Notifications REST clients, and BFF gateway clients.
- Update BFF GraphQL query/mutation resolvers and REST gateway adapters; do not add database access to `app/bff`.
- Extend Expense Core sync revision handling (`JpaSynchronizationStore.kt`, `SyncController.kt`) only where the existing revision is semantically suitable; do not equate every domain revision with PostgreSQL replay LSN without documentation.
- Add integration tests for command response followed by query, BFF fanout, stale reader, and writer fallback under `app/bff/src/test`, service tests, and `tests/acceptance/`.

## Current increment

`libs/db` now models a causal position as a PostgreSQL LSN rather than a wall
clock value. Reader health stores the latest replayed watermark, and a query
with a required watermark cannot use a reader until that position is observed;
eventual/bounded queries use the explicit bounded writer fallback while other
queries remain writer-routed. Stateful services now validate and propagate the
required watermark through a shared servlet filter and emit the writer LSN
after successful mutating requests. The reactive BFF captures and forwards the
required watermark to downstream gateways. Downstream writer watermark headers
are now copied to the inbound BFF response when available. Full end-to-end
causal command/query evidence remains open.

## Filter hardening (2026-09-22)

`DbCausalWatermarkFilter` now attempts to emit the writer watermark for every
successful non-GET response after the downstream chain returns. It no longer
prevents the attempt solely because the servlet response is marked committed;
the servlet container safely ignores a header mutation that is already too late,
while uncommitted mutation responses retain the watermark. The DB library test
suite passed after this change; live multi-service causal propagation remains
open.

`DbCausalWatermarkFilterTest` now uses a mocked writer connection and servlet
boundary to prove the inbound required LSN is visible during downstream
processing and that a successful mutation emits the current writer LSN. The
test also verifies the thread-local causal requirement is restored afterward.

The BFF watermark merge is now centralized in `greatestWriterWatermark`, which
rejects malformed values and preserves the greatest valid downstream LSN.
`RestGatewayTest` covers increasing, decreasing, missing, and malformed
watermarks. Live multi-service causal E2E remains the final DB-10 evidence gap.

`tests/e2e/test_causal_watermark.py` now performs a live authenticated Accounts
mutation, captures `X-Squarewise-Writer-Watermark`, and sends it on the follow-up
profile query. Against the replica-enabled Compose stack it returned a writer
watermark and HTTP 200 for the causal follow-up query; `py_compile` passed.

## Task closure (2026-09-28)

DB-10 is complete. Causal PostgreSQL LSN watermarks are validated, parsed,
propagated through servlet filters in stateful services, and forwarded and merged
through BFF WebFlux response streams. Unit regression coverage in `libs/db` and
`app/bff`, along with live E2E probe validation in `tests/e2e/test_causal_watermark.py`,
confirms that read-after-write causal ordering functions across services.
